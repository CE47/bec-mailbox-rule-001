01 / Brief

The evidence was built to look ordinary.

Work from the telemetry. Establish what happened, when it happened, and whether the mailbox was compromised.

A foreign sign-in. A quiet inbox rule. One destination outside the organisation.

An external actor who obtained a user’s credentials logged into the corporate email tenant from a suspicious foreign IP, created an inbox rule to silently hide replies from the finance team, and enabled external forwarding of all mail to an attacker-controlled address.

This is the shape of a Business Email Compromise investigation: correlate authentication and Microsoft 365 audit events, build the sequence of events, and support your verdict with concrete observations.

Signal 01

Foreign access

Confirm the sign-in origin, account, and timing across Windows-style authentication events.

Signal 02

Mailbox stealth

Identify the new inbox rule and inspect its name and matching condition.

Signal 03

External exfiltration

Trace the forwarding change and identify the destination address.

CTIA Scenario Lab / bec-mailbox-rule-001 / SOC Investigation Brief

Foreign sign-in. Stealth inbox rule. External forwarding.

A user account signed in to the email tenant from an unfamiliar foreign IP. Shortly afterwards, the mailbox had an inbox rule created and external mail forwarding enabled.

Scenario ID bec-mailbox-rule-001
Alert name Suspicious mailbox activity — possible Business Email Compromise (BEC)
Severity High · escalate on confirmation
01

Scenario briefing

Your organisation uses Microsoft 365 for corporate email. Sign-in and audit telemetry is shipped into Elastic, and a detection rule has fired.

!
Detection signal

A user signed in from an unfamiliar foreign IP, then the mailbox had an inbox rule created and external forwarding enabled.

This is the classic shape of Business Email Compromise. An attacker who has stolen a user’s password logs into their mailbox and then:

  • Creates a hidden inbox rule — often named to look boring, such as “Move to Conversation History” — that quietly files or hides replies about invoices or payments so the real user never notices the fraud.
  • Turns on external forwarding — silently copying incoming mail to an attacker-controlled address so they keep reading the victim’s email after the session ends.

Confirm the suspicious sign-in, find the inbox rule and forwarding change, identify the forwarding destination, build a timeline, and write an incident report.

!Do not read the solution file. Investigate as if this were a live incident.

04

The investigation query

Run this in Discover against the cloud-* data view, with the time range set to 2026-09-22 00:00:00.000 → 2026-09-22 23:59:59.999 UTC:

KQL / Discover(event.action: "mailbox_rule_created" or event.action: "external_forwarding_enabled") and user.name: "kpatel"
  • event.action: "mailbox_rule_created" — an inbox rule was created.
  • event.action: "external_forwarding_enabled" — external mail forwarding was turned on.
  • user.name: "kpatel" — the mailbox named in the alert.

This query isolates the two mailbox-configuration changes on the flagged account. Add o365.operation, email.rule.name, and email.forwarding.target as columns to see the rule name and forwarding destination.

05

Expected shape of the answer

Do not expect a number here — you will derive it. Your findings should take this specific shape:

  1. In auth-*, a failed logon (event.code: 4625) followed by a successful logon (event.code: 4624) for kpatel from the same foreign IP within a few minutes.
  2. In cloud-*, an inbox rule created event on that mailbox. Note its email.rule.name and the condition it matches.
  3. In cloud-*, external forwarding enabled. Note the email.forwarding.target.
  4. All activity by the same user from the same foreign IP in a short window, ending with a logoff.
Suspicious pattern

A foreign sign-in immediately followed by a hidden inbox rule for invoice or payment mail, plus forwarding to an external, non-corporate address.

Benign pattern

Sign-ins from expected locations, no new inbox rules, and no forwarding to outside domains.

01

Words you need to know

Alert

A rule that fires when something looks dangerous. It is a hint, not a fact; investigators confirm or dismiss it.

Index / data view

A named collection of records with the same shape. This lab has auth-* and cloud-*. Older Kibana versions call a data view an index pattern.

NDJSON

Newline-Delimited JSON: one JSON object per line. The event files are auth.ndjson and cloud.ndjson.

Index template

A configuration that gives fields their correct types before data arrives. This prevents Elasticsearch from guessing and silently breaking searches.

Elasticsearch

The database that stores and searches the logs. It answers requests at http://localhost:9200.

Kibana

The web interface used for the investigation. It lives at http://localhost:5601.

IOC

An indicator of compromise: evidence that something bad happened. An address such as kpatel.backup@mail-exfil.example is an IOC if you find it.

External / foreign IP

A sign-in from an address your users do not normally use. The suspicious address in this lab belongs to a 203.0.113.x documentation range.

M365 audit log

A record of actions in Microsoft 365, including sign-ins, inbox-rule creation, and forwarding changes, with an operation and action.

Inbox rule

An automatic mailbox rule. Attackers use one to hide replies so the victim does not notice fraud.

External forwarding

Automatic copies of incoming mail sent to another address, allowing an attacker to keep reading the victim’s mail.

Business Email Compromise

A mailbox takeover used for invoice fraud, payment fraud, or information theft, often concealed with inbox rules and forwarding.

ECS field

A standardised dotted field such as user.name, source.ip, event.code, event.action, email.rule.name, or email.forwarding.target.

False positive

The alert fired, but nothing bad happened.

True positive

The alert fired, and something bad actually happened. Your investigation must decide which verdict is supported.

Create the two Kibana data views

What to do

Open Kibana at http://localhost:5601, then open Stack Management → Data Views → Create data view.

Auth data view

Name auth, pattern auth-*, timestamp field @timestamp, then save.

Cloud data view

Two saved data views named auth and cloud. Without them, every query can return no results.

05

Open Kibana

Open or continue in your web browser and go to http://localhost:5601. You should see the Kibana login or home screen. Kibana lets you search the logs without touching a database directly.

06

Open Discover

What to click

Open the navigation menu and choose Discover under Analytics.

What you should see

A search bar, a field list on the left, and a document list below. This is where queries are written and answers are read.

07

Select the auth data view

Use the data-view selector at the top of Discover and choose auth. The field list should include event.code, user.name, and source.ip. Start with sign-in logs, then pivot to the cloud audit log.

08

Set the time range

What to do

In the time picker, choose Absolute. Set From to Sep 22, 2026 @ 00:00:00.000 and To to Sep 22, 2026 @ 23:59:59.999, then apply.

What you should see

@timestamp spans the full UTC day. A narrower range silently hides relevant events.

09

Query the suspicious sign-in

KQL / auth data viewuser.name: "kpatel" and (event.code: 4624 or event.code: 4625)
What you should see

A small set of sign-ins for kpatel. Add event.code, event.outcome, and source.ip as columns.

What to notice

A failed logon (4625) followed by a successful logon (4624) from the same foreign IP. Write down the user, IP, and both timestamps.

10

Switch to the cloud audit log

KQL / cloud data viewuser.name: "kpatel"

Change the data view from auth to cloud. Add event.action, o365.operation, and source.ip as columns. Look for two configuration changes from the same foreign IP: one creating an inbox rule and one enabling forwarding.

11

Isolate the mailbox changes

KQL / malicious mailbox changes(event.action: "mailbox_rule_created" or event.action: "external_forwarding_enabled") and user.name: "kpatel"

Add email.rule.name, email.rule.condition, and email.forwarding.target as columns.

  • Note the deliberately boring inbox-rule name and the invoice or payment condition used to hide finance replies.
  • Note the external forwarding target and confirm that its domain is outside the company.

This is the same core query used in the standard investigation brief. A stealth rule plus forwarding to an outside address is the central BEC evidence. Write down the rule name, condition, and destination.

12

Build the timeline

Open a note and list each finding from oldest to newest using the exact @timestamp:

  1. Failed logon for kpatel from the foreign IP.
  2. Successful logon for kpatel from that same IP — account takeover.
  3. Inbox rule created to hide invoice or payment mail.
  4. External forwarding enabled to the outside address.
  5. Logoff.

The result should read as a clean sequence: get in, hide replies, forward mail out, leave. This timeline is the evidence of cause and effect and the heart of the report.

13

Write the report

Summary

Fill in what happened, which mailbox, and your verdict.

Example: On 22 September 2026, kpatel was accessed from a foreign IP after a failed-then-successful sign-in. The attacker created a hidden inbox rule and enabled external forwarding to an outside address. This is a true positive Business Email Compromise.

Timeline

Fill in the five stages from Step 12 with exact UTC timestamps.

Evidence

List every query and the fact it proved.

The auth-* query proves the failed-then-successful sign-in from a foreign IP. The cloud-* query proves the stealth inbox rule and external forwarding, including the destination.

Verdict

State True Positive or False Positive and explain why.

A foreign sign-in on a stolen credential, followed by a hidden inbox rule and external forwarding to an attacker-controlled address, forms a coherent Business Email Compromise chain.

Recommendations

Give at least three concrete actions.

Revoke sessions and reset the password with MFA. Remove the malicious inbox rule and disable forwarding. Block the destination domain and foreign IP. Search other mailboxes for similar rules and review finance mail for fraud.
