# CTIA Scenario Lab — bec-mailbox-rule-001

A self-contained SOC analyst training scenario built from a deterministic, ECS-compliant synthetic dataset. Investigate it with Elasticsearch + Kibana.

## Scenario narrative

An external actor who obtained a user's credentials logged into the corporate email tenant from a suspicious foreign IP, created an inbox rule to silently hide replies from the finance team, and enabled external forwarding of all mail to an attacker-controlled address.

The dataset is built from 2 log sources:

| Source | What it covers |
|---|---|
| `auth` | Windows security-style authentication events: logons, logoffs, failures, lockouts, process starts |
| `cloud` | Microsoft 365 audit events: sign-ins, inbox-rule creation, mailbox forwarding changes, and file/mail operations, with the operation, workload, acting user, and source IP |

The logs are **synthetic and deterministic**: they are generated with a fixed seed, so every run produces byte-identical data. Event volume is engineered to sit in the 200–600 range expected for a realistic, noisy-but-reviewable lab.

## Contents

| File | Description |
|---|---|
| `auth.ndjson` | auth events (271 documents, NDJSON — one JSON object per line) |
| `auth.json` | Elasticsearch index template — field types for the `auth-*` index |
| `cloud.ndjson` | cloud events (149 documents, NDJSON — one JSON object per line) |
| `cloud.json` | Elasticsearch index template — field types for the `cloud-*` index |
| `guided-walkthrough.md` | Step-by-step investigation guide for beginners |
| `instructions.md` | Compact investigation brief (standard version) |

## Requirements

- A running **Elastic Stack** (Elasticsearch + Kibana). Kibana is required for the guided investigation steps.
- `curl` for data ingestion.

No Python, packages, or local servers are needed to run the lab — the data is pre-generated and distributed as plain files.

## Quick start

Run every command from this folder.

```bash
# 1. Check Elasticsearch is up
curl -s localhost:9200/_cluster/health

# 2. Install the index templates (fixes field types)
curl -s -XPUT localhost:9200/_index_template/auth -H 'Content-Type: application/json' --data-binary @auth.json
curl -s -XPUT localhost:9200/_index_template/cloud -H 'Content-Type: application/json' --data-binary @cloud.json

# 3. Import the data (the bulk API needs one action line + one data line per doc)
for s in auth cloud; do
  while read -r l; do
    echo '{"index":{"_index":"'$s'-2026.09.22"}}'
    echo "$l"
  done < $s.ndjson | curl -s -XPOST localhost:9200/_bulk -H 'Content-Type: application/x-ndjson' --data-binary @-
done

# 4. Verify (expect the document counts from the Contents table)
curl -s localhost:9200/_cat/indices/auth*,cloud*

```

Then open Kibana, create a **data view** for each index pattern (`auth-*`, `cloud-*`, timestamp field `@timestamp`), and follow [`guided-walkthrough.md`](./guided-walkthrough.md) for the full investigation — or hand the investigation directly to seasoned analysts with [`instructions.md`](./instructions.md).

## How the dataset is produced

The scenario is generated by a deterministic Python pipeline (seeded PRNG, ECS-aligned field mappings, `@timestamp` in ISO 8601 UTC with millisecond precision). Generators, mappings, an offline mock Elasticsearch, and a validator that checks schema, determinism, and ground truth live in the upstream project — `scenario.config.json` is the contract that fixes the seed, the noise budget, and the expected outcomes for each run.

The student package exposes only the artifacts the analyst needs: the NDJSON datasets, the index templates, and the two documents you are reading.
